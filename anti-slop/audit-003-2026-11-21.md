# Colour-token audit — 2026-11-21

Scope: source inspection of src/**/*.tsx and src/**/*.css, DESIGN.md, and WCAG sRGB contrast calculations. No production UI changes. This is not a browser/computed-style audit; image backgrounds, native checkbox rendering, CSS cascade, and complete interactive states still require rendered verification. Mode: AFTER (session override).

## Verdict

The amber/forest palette is sound. Its application is not fully tokenized, and focus treatments need attention. Keep the brand colours; fix their implementation rather than redesigning the palette.

Inventory: 25 colour declarations in globals.css (10 current + 15 compatibility aliases), resolving to 9 distinct values. Across public source, including globals.css: 367 hexadecimal occurrences in 25 files, 11 distinct hex values. These are source occurrences, not rendered colour counts. Admin has no hex literals but uses Tailwind neutral, red, blue and emerald utilities alongside the global brand aliases.

## Numbered findings

### 1. HIGH — Dark-surface focus colour is not consistently scoped (R-32, R-25)

Evidence: src/app/globals.css:106–116 gives all focus indicators forest; only descendants of data-surface="forest" and header get amber. src/components/PetTransportPricing.tsx:407 creates a forest results panel without that attribute, containing a checkbox, select and WhatsApp link (around lines 513–551). Forest focus can disappear against the panel. Admin dark neutral surfaces also inherit the forest outline, except header descendants, which receive amber via a broad global selector.

Recommendation: mark dark public surfaces and explicitly scope an appropriate admin focus colour. Verify focused checkbox, select and CTA in the browser. Do not assume the light-only public theme means there are no dark surfaces.

### 2. HIGH — Input utilities explicitly suppress the shared focus outline (R-32)

Evidence: src/components/AddressSearchInput.tsx:182 and src/components/PetTransportPricing.tsx:353 use focus:outline-none. Their replacement is only a 1px border changing from #333333 or ink to forest. This is a weak focus distinction rather than the documented 3px indicator.

Recommendation: remove the suppression and preserve the shared focus-visible outline, or use an equally visible local replacement. Verify computed styles and keyboard navigation; this finding identifies the source conflict, not a measured screenshot failure.

### 3. LOW — The token layer is bypassed extensively (R-29, R-31)

Evidence: 367 public-source hex occurrences; forest appears 157 times, amber 61. Shared Button.tsx:30–36, Header.tsx:47–126, Hero.tsx and PetTransportPricing.tsx all embed token-equivalent literals, including shadow strings. Changing --color-accent alone will not change these elements.

Recommendation: use existing bg-accent, text-forest, border-line and hover:bg-accent-hover utilities; use CSS variables inside arbitrary shadows and SVG fills. Keep the legacy names as aliases, ideally referencing the canonical variables rather than repeating their values. No new theme framework needed.

### 4. LOW — Map colours and a stale lime shadow bypass the documented palette (R-29, R-31)

Evidence: src/components/BaliZoneMap.tsx:13–16 defines zone fills #CEE2C5, #FEBB00, #EDE6C9 and #8FBDB0. The last two have no named theme tokens or documented role. Line 75 still has rgba(178,210,53,0.35), i.e. the old #B2D235 lime, despite the previous hex-only search finding none.

Recommendation: replace the stale shadow with a brand colour. Keep category colours only if their wayfinding role is documented and given map-specific tokens; do not force every zone to the same colour. Zone labels already help avoid colour-only communication.

### 5. LOW — Colour documentation contains incorrect ratios and incomplete roles (R-31)

Evidence: DESIGN.md lists ink/white as 9.62:1; the actual #3D3D3D / #FFFFFF ratio is 10.86:1. globals.css repeats 9.6:1. DESIGN.md omits accent-hover and sagewash from its table. globals.css describes sagewash #F4F9EE as a 5% sage wash, but that literal is not the result of mixing 5% #CEE2C5 into white. Amber's stated restriction to the mark/actions conflicts with actual amber headings, decorative rules, shadows and footer labels.

Recommendation: record the true ratios and actual roles. Treat sagewash as an intentional named surface rather than claiming an inaccurate mixing formula. Decide whether the wider amber use is intentional before enforcing the old prose.

### 6. LOW — Functional/status colours and surface roles are implicit (R-29, R-31)

Evidence: globals.css defines primitive/legacy colours but no canonical surface, on-dark, muted, focus or error roles. Public calculator errors use text-red-700; admin Toast.tsx uses red/blue status utilities and AdminHeader.tsx uses emerald success. These are legitimate status colours, not automatically brand violations, but they are outside the documented token contract. Header :focus-visible is globally amber, coupling public and admin headers.

Recommendation: document a minimal semantic mapping using the existing palette, with scoped admin exceptions and shared error/status roles where actually reused. Preserve readable red/blue/emerald states; don't replace meaningful errors with amber simply to shrink the palette.

## Additional boundary checks

Button.tsx:34 uses forest/35 on a transparent surface (1.97:1 over white). PetTransportPricing.tsx:281 uses forest/40 (2.21:1 over white); line 323 uses forest/25 (1.60:1). These outlines alone are below 3:1. Their dark labels/icons may already identify the controls sufficiently, so this source-only audit does not label them automatic WCAG failures. Check rendered affordances before deciding to strengthen boundaries. Decorative sage rules are not failures merely because they are low contrast.

## Suggested approval order

1–2: keyboard visibility first. 3–4: make the existing palette reliable. 5–6: align documentation and semantics. No source changes made; fixes require approval by finding number.
